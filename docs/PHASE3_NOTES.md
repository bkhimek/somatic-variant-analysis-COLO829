**What that means concretely:** running this against current data should produce a `som.stats.csv` showing 0 true positives, 0 false positives, and however many false negatives the truth set contains (since there's essentially nothing in the query VCF to match). That's the expected, correct outcome for this test — not a bug. Do not read anything into the actual precision/recall numbers from this run; the only thing worth checking is that `som.py` runs to completion without erroring. (Note: this is the second tool tried here — `hap.py` couldn't even reach this "runs cleanly, produces zeros" state, since it hard-fails outright on a GT-less VCF; see "Second run — findings" below. ## First run — findings (2026-08-30)

**Real bug: `PREPARE_TRUTH_VCF`'s container tag, `quay.io/biocontainers/htslib:1.21--h566b1c6_0`, doesn't exist** — Docker failed with `manifest unknown`. That tag was pattern-matched off the already-confirmed `samtools:1.21--h50ea8bc_0` image's build-hash convention rather than actually checked against the registry, which was the mistake — this project's own established standard (see the bwa-mem2 memory correction, the Mutect2 memory research) is to verify container/version claims for real before shipping them, and this one slipped through. Verified properly via research afterwards rather than guessing a second time: real htslib 1.21 tags do exist (`1.21--h566b1c6_1`, note the `_1` not `_0`, or `1.21--h5efdd21_0`), but the better fix is to **not pull a second image at all** — `samtools:1.21--h50ea8bc_0` (already confirmed working in this pipeline since Phase 1) bundles `bgzip`/`tabix` too, because bioconda's samtools recipe pulls in htslib as a genuine runtime dependency (via htslib's own `run_exports` mechanism, not just a build-time link), which installs those binaries into the same conda environment. **Fix:** `PREPARE_TRUTH_VCF` now reuses `samtools:1.21--h50ea8bc_0` instead of a separate htslib image.

**Real finding, fully resolved after extensive forensics: the COLO-829 HiSeqX truth-set file is corrupted at the source, in NYGC's own published archive — not fixable, and not usable.** `tabix` failed indexing the bgzipped truth VCF with `[E::get_intv] Failed to parse TBX_VCF` and `[E::hts_idx_push] Chromosome blocks not continuous`, on lines like `"PaxHeader/COLO-829-NovaSeq--COLO-829BL-NovaSeq.snv.indel.final.v6.annotated.vcf"`, `"18 uid=2056607721"`, `"SCHILY.dev=..."` — literal POSIX PAX extended tar-header text sitting inside what should be pure VCF content.

Diagnosing this took several rounds, each ruling out a progressively deeper cause, documented here because every round was a genuinely different, real possibility that needed to be eliminated with evidence rather than assumed:
1. **Ruled out: bad extraction command.** A fresh, full, unfiltered `tar xf` into a clean directory produced the identical corruption — not something caused by how the file was originally isolated from the archive.
2. **Ruled out: GNU tar CLI bug.** Python's `tarfile` module — a completely independent implementation — extracted the exact same corrupted bytes for this member. Two unrelated parsers agreeing rules out a reader-specific bug.
3. **Ruled out: download/transfer corruption.** A fresh re-download of the 70.2MB archive produced a byte-identical SHA-256 hash to the original. Whatever's wrong was wrong before it ever reached this machine.
4. **Confirmed: the archive's own internal accounting is exact and self-consistent** (`tarfile`'s full member table showed every entry's declared data range ending exactly where the next entry's header begins, no drift or overlap anywhere) — which at first seemed to rule out corruption entirely, until byte-level inspection showed the corrupted entry's *own, correctly-bounded* 36,165,120-byte data region does not contain COLO-829 HiSeqX content. It contains the archive's other five VCF files (COLO-829 NovaSeq, both HCC-1143 platforms, both HCC1187 platforms) concatenated together, each with its own genuine embedded tar header. The arithmetic is exact: those five files' real sizes sum to 36,155,347 bytes, and adding the expected ~8,237 bytes of per-fragment header overhead accounts for the corrupted entry's full size with nothing left over and nothing missing. **The real COLO-829 HiSeqX SNV/indel VCF simply isn't present anywhere in this archive.**
5. **Confirmed no fix exists anywhere:** researched the GitHub repo directly — only 7 commits, all from 2026-05 (a from-scratch reconstruction of the original 2019 site, likely from an old web-archive snapshot), the corrupted archive untouched since its one commit, no tags/releases/alternate branches, zero GitHub issues (open or closed) reporting this, and the paper's own data-availability statement points back to this same site with no separate mirror. Independent corroboration: the repo's own README claims this archive is 140MB, but the actual committed blob is 70.2MB — almost exactly half — and a second archive in the same repo (`Variants.Downsampled.tar.gz`) shows the identical ~50% shortfall. This is a systemic data-loss event affecting the whole repo, not an isolated glitch in one file.

**Decision (made with the user 2026-08-30): switch the primary Module 5 truth set from COLO-829 HiSeqX to COLO-829 NovaSeq** — the same archive's NovaSeq VCF for this cell line pair, confirmed intact (clean `##fileformat=VCFv4.2` header, exactly one `#CHROM` line, no embedded tar artifacts, cleanly bounded per the full member table). This reopens the platform-mismatch caveat the original HiSeqX choice was specifically meant to minimize (`data_sources.md` §3 — our PRJEB27698 FASTQs are HiSeq X Ten, not NovaSeq), which now needs to be stated plainly alongside any Module 5 results rather than assumed away. No pipeline code changes were needed for this switch — `modules/benchmarking.nf` is agnostic to which truth VCF it's given; only `--truth_set_vcf` needs to point at the NovaSeq file instead. Full evidence trail and the revised extraction commands are in `docs/data_sources.md` §3.

**Cosmetic, non-blocking: a Nextflow `WARN` about a useless `.first()` call.** `PREPARE_TRUTH_VCF.out.truth_vcf_indexed.first()` triggered `WARN: The operator 'first' is useless when applied to a value channel which returns a single value by definition`. Harmless (the channel already only ever emits once either way) but easy to clean up: `PREPARE_TRUTH_VCF`'s only input is a plain value (not a channel), so Nextflow already treats a process with all-singleton-value inputs as producing a value-channel output — `.first()` on it is redundant. Removed. (The identical latent pattern exists in `INDEX_FASTA`/`CREATE_SEQUENCE_DICTIONARY`'s `.first()` calls from Phase 2, but their build branches have never actually executed in any run so far — always hit the pre-existing-`.fai`/`.dict` shortcut instead — so this hasn't surfaced there yet. Left alone rather than touched, since that's already-signed-off Phase 2 code and this warning is cosmetic, not a correctness issue.)

## Second run — findings (2026-08-30)

**Real bug: `HAPPY_BENCHMARK`'s container tag, `quay.io/biocontainers/hap.py:0.3.15-0`, doesn't exist** — same root cause as the first run's htslib tag miss: guessed by pattern-matching rather than checked, and biocontainers tags are always `<version>--<conda-build-string>` (double dash), not `<version>-<N>`. Researched (found the real tag via a GitHub issue reference, since this sandbox can't browse quay.io directly) and, this time, explicitly asked the user to confirm with a real `docker pull` before shipping the fix rather than risk a third guess — confirmed working: `quay.io/biocontainers/hap.py:0.3.14--py27h5c5a3ab_0`.

**Real, much more significant bug: `hap.py` is the wrong tool for this comparison entirely.** With the container pulling correctly, `hap.py` ran but reported `Non-reference VCF records: 0` for the truth VCF — despite that VCF genuinely containing 43,192 records — and then hard-failed with `Input files/regions do not contain variants (0 haplotype blocks were processed).` and a Python traceback.

Root cause: `hap.py` is GA4GH's benchmarking tool for **germline** small-variant calls, and it decides whether a VCF record counts as "non-reference" (i.e. a real call worth comparing) by reading the record's `GT` (genotype) field — `0/1`, `1/1`, and so on. Both the NYGC somatic truth VCF and Mutect2's own `FilterMutectCalls` output annotate calls with `AD`/`DP`/`AF` (allele depth/depth/allele fraction) per sample, which is the correct convention for **somatic** calling — there's no diploid genotype to call in a tumour-normal comparison, only "this ALT allele is present at this fraction." Neither VCF carries a `GT` field at all. With no `GT` to read, `hap.py` silently treated every single truth record as homozygous-reference (`0/0`), which is indistinguishable from "no variant here" — hence "0 non-reference records" on a 43,192-record file, and then a hard failure once `hap.py` found literally nothing to build a comparison out of.

This is not a flag or config hap.py needs — it's a structural mismatch between what hap.py is built to read and what a somatic VCF contains. Confirmed via Illumina/hap.py's own README/documentation: the same package ships two distinct tools for exactly this split — `hap.py` for germline (GT-based) comparison, and **`som.py`** for somatic (GT-less) comparison, which instead judges a match purely on ALT-allele presence (using `bcftools isec` internally), with no genotype/haplotype matching involved. Both tools ship in the identical container image — `quay.io/biocontainers/hap.py:0.3.14--py27h5c5a3ab_0` already pulled for the (wrong) `hap.py` invocation also contains `som.py` — so no new image or version research was needed, only a different binary and different flags.

Output filenames were confirmed by inspecting `som.py`'s own source rather than guessed (to avoid repeating the kind of output-declaration mismatch this project has hit before): a bare `-N` (normalize both VCFs before comparing — som.py's own documented recommendation for a first run) unconditionally writes `som.stats.csv` and `som.metrics.json`; adding `--happy-stats` produces the friendlier `som.summary.csv` table, giving roughly the same headline view `hap.py`'s own `summary.csv` would have.

**Fix:** renamed the process `HAPPY_BENCHMARK` → `SOMPY_BENCHMARK`; script now runs `som.py <truth> <query> -r <reference> -o som -N --happy-stats` instead of `hap.py`; output declarations changed to `som.stats.csv`/`som.summary.csv`/`som.metrics.json`/`som.*`; all downstream references (`workflows/somatic.nf`'s include/call/emit — now `sompy_summary` — plus `main.nf`, `README.md`, and `docs/data_sources.md`'s hap.py mentions) updated to match. No new container pull required. (The `--happy-stats` part of this fix turned out to be its own bug — see "Third run — findings" immediately below.)

## Third run — findings (2026-08-30)

**Real bug: `som.py --happy-stats` needs flags it wasn't given, and hard-fails immediately (before comparing anything) without them.** With the `som.py` switch landed and `PREPARE_TRUTH_VCF` reused from cache, `SOMPY_BENCHMARK` ran but exited 1 before doing any real work:

```
ERROR    Obtaining hap.py stats only works when a feature table is selected, and when using unfiltered variants. Specify -P --feature-table <...> or use --roc to select a ROC type.
```

Traced to `som.py`'s own argument parser (confirmed via the upstream Illumina/hap.py source, not guessed): `--happy-stats` — the flag added specifically to get the friendlier `som.summary.csv` table — is only accepted together with either `-P` (count non-PASS/filtered variants too, not just PASS) plus `--feature-table <name>` (a caller-specific feature-extraction profile, e.g. for GATK/Mutect2-style output), or `--roc <type>` (a specific ROC curve type). None of those were supplied, so the flag combination itself was invalid and `som.py` refused to run at all — this has nothing to do with the truth VCF, the query VCF, or anything data-related; it's a same-as-`hap.py`-flags-but-different-requirements gap in the command line itself.

Picking a `--feature-table` value or `--roc` type correctly would mean matching it to Mutect2's actual VCF annotation conventions — exactly the kind of "get the real precision/recall numbers right" work this first cut is deliberately not doing yet (see "Scope decision" at the top of this file: the query VCF has zero calls regardless, so no feature-table choice changes today's result). **Fix:** dropped `--happy-stats` entirely rather than chase the right combination of extra flags for no present benefit. `som.py -N` alone (no `--happy-stats`) still unconditionally writes `som.stats.csv` and `som.metrics.json` — confirmed via the same source read — which is sufficient to prove the DAG/container/command line are wired correctly; the `som.summary.csv` headline table is deferred until Phase 3 is revisited for real precision/recall numbers, at which point the right `--feature-table`/`--roc` choice can be researched properly rather than guessed. `workflows/somatic.nf`'s final emit was renamed `sompy_summary` → `sompy_stats`, now pointing at `SOMPY_BENCHMARK.out.stats`. Not yet re-run.

## Design choices made, and why (so you can sanity-check them)

1. **`som.py`, not `hap.py`.** See "Second run — findings" above for the full root cause — `hap.py` is GA4GH's germline (GT-based) comparison tool and silently can't read a GT-less somatic VCF at all; `som.py` (same container, same package) is Illumina's own somatic-specific tool, built for exactly this ALT-allele-presence comparison, with no GT/haplotype matching involved.
2. **No confidence-region BED restriction.** Confirmed in Phase 0 (`data_sources.md` §3): NYGC does not publish a high-confidence callable-regions BED for SNV/indel, only a CNV bed and SV bedpe (neither applicable here). `som.py` runs unrestricted across the whole genome. This was a Phase 0 finding, not a new decision.
3. **`-N` (normalize), no `--happy-stats`.** `-N` normalizes both VCFs before comparing — `som.py`'s own documented recommendation for a first run. `--happy-stats` (which would add the friendlier `som.summary.csv` headline table) was tried and dropped — found via execution (see "Third run — findings" above) that it requires `-P` + `--feature-table <name>` or `--roc <type>`, and picking the right one of those means matching Mutect2's actual VCF conventions, which is real-precision-numbers work this first cut isn't doing yet. Plain `-N` still writes `som.stats.csv`/`som.metrics.json`, which is enough to prove the wiring. `som.py` doesn't have an engine choice (xcmp vs vcfeval) or a `--pass-only` flag the way `hap.py` does — those design questions from the original `hap.py`-based draft of this section don't carry over; `som.py`'s comparison is a simpler ALT-presence set operation (`bcftools isec` under the hood), and it does not itself filter on the VCF `FILTER` column, so `FILTER_MUTECT_CALLS`' non-PASS calls are not automatically excluded the way they would have been under `hap.py`'s default. This is a real, open item to revisit once real full-genome Mutect2 output exists and non-PASS calls actually appear in the query VCF (today's `dev`-profile query VCF has zero calls of any kind, so it doesn't yet matter in practice).
4. **Truth VCF bgzip/tabix handled automatically, mirroring Phase 2's resource-VCF pattern**, rather than asking you to prep it by hand first. `data_sources.md` already confirmed the file NYGC ships is plain uncompressed VCF, not `.vcf.gz` — `PREPARE_TRUTH_VCF` bgzips and indexes it the first time, and auto-detects/skips on later runs if you've already done this yourself.

## Real, unverified risk worth flagging before you run this

**Contig-naming and reference-build match between the truth VCF and our reference FASTA has not been directly checked yet.** The NYGC truth set was generated by NYGC's own pipeline against their own reference build (`data_sources.md` §3's lineage-mismatch caveat already covers this at the calling-methodology level) — but the more basic, mechanical question of whether its VCF header uses `chr`-prefixed contig names (matching `Homo_sapiens_assembly38.fasta`, the Broad reference this pipeline aligns against, per `dev_intervals.bed`'s note that Broad's convention is `chr`-prefixed) hasn't been confirmed by actually looking at the truth VCF's header. **Update 2026-08-30: actually already visible from the corruption diagnosis above** — the clean tail content recovered from the (corrupted) HiSeqX entry showed rows like `chrX  155168078  ...`, `chr`-prefixed, matching our reference. The NovaSeq file now in use is from the same NYGC pipeline/convention, so this is a low-risk item, but still worth a quick confirming glance (`zcat truth_set/COLO-829-NovaSeq--COLO-829BL-NovaSeq.snv.indel.final.v6.annotated.vcf.gz | grep '^##contig' | head`) rather than fully assumed. If they don't match, `som.py` (via `bcftools isec` underneath) will fail fast with a clear contig-mismatch error rather than silently producing wrong numbers, so this isn't a silent-corruption risk either way.

## How to run it (once you've checked the items above)

```bash
conda activate nextflow
cd ~/projects/somatic-variant-analysis-COLO829

nextflow run main.nf -profile docker,dev \
    --tumour_reads_1        fastq_dev_sample/TUMOUR_R1.sample.fastq.gz \
    --tumour_reads_2        fastq_dev_sample/TUMOUR_R2.sample.fastq.gz \
    --normal_reads_1        fastq_dev_sample/NORMAL_R1.sample.fastq.gz \
    --normal_reads_2        fastq_dev_sample/NORMAL_R2.sample.fastq.gz \
    --reference_fasta       reference/Homo_sapiens_assembly38.fasta \
    --panel_of_normals      reference/1000g_pon.hg38.vcf.gz \
    --germline_resource     reference/af-only-gnomad.hg38.vcf.gz \
    --common_biallelic_sites reference/small_exac_common_3.hg38.vcf.gz \
    --truth_set_vcf         truth_set/COLO-829-NovaSeq--COLO-829BL-NovaSeq.snv.indel.final.v6.annotated.vcf \
    -resume
```

(Path above uses the **NovaSeq** file — the originally-planned HiSeqX file is corrupted at the source and unusable, see "First run — findings" above and `data_sources.md` §3. Adjust the path if you extracted it somewhere else.) `-resume` reuses everything already computed for Modules 1–4 and, per the last successful run, `PREPARE_TRUTH_VCF` too — so this should now only actually execute the fixed `SOMPY_BENCHMARK` step.

Expected new outputs:
- `results/benchmarking/truth_set/<truth_vcf_basename>.vcf.gz` (+ `.tbi`)
- `results/benchmarking/som.stats.csv` — TP/FP/FN counts by variant type; expect all zeros/near-zeros against current dev-profile data — see "Status" above
- `results/benchmarking/som.metrics.json`, plus `som.py`'s other standard output files (no `som.summary.csv` in this first cut — `--happy-stats` was dropped, see "Third run — findings" above)

Per the caveat above, don't be surprised (or alarmed) by `som.stats.csv` showing 0 TP/0 FP against the current data — check that the pipeline **ran to completion without errors** first, same split every phase so far has established.
